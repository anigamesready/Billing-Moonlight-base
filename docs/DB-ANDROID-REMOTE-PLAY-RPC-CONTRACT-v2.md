# Remote Play client API contract — DB Android

Status: **implementation contract for the separate DB Android backend; not yet deployed**.

This contract is consumed by the application in this repository. The backend source remains in the separate `anigamesready/PC-Billing` repository. No DB code, migrations or deployment artifacts are copied into this Moonlight repository.

## Transport and endpoint configuration

- Control plane: the existing DB Android Node API over its configured HTTPS gateway.
- The Android app and Host Agent must use the exact API base URL already configured by the Ani Games Ready DB Android deployment. Do not invent a new hostname, use `127.0.0.1` from a customer phone, or use a temporary Quick Tunnel URL for production.
- The current Node API route shape is `POST /rest/v1/rpc/<function>`; authenticated calls carry the appropriate raw token in `Authorization: Bearer <token>`.
- The source currently documents local loopback ports 8787 (main) and 8788 (isolated stage). These are not customer-facing addresses. The active, stable HTTPS gateway and the method by which the app receives its configured base URL still require confirmation.
- No Supabase URL, SDK, key, project reference, Edge Function or database credential is allowed in either client.
- The DB Android HTTPS API carries control JSON only. It is not the Sunshine/Moonlight TCP/UDP media transport.

## Identity and token contract

### Customer login

`remote_play_login` is unauthenticated at the HTTP layer but rate-limited by the Node API (IP, normalized rental code and activation credential). It accepts:

| Argument | Type | Purpose |
|---|---|---|
| `p_rental_code` | text | Existing rental account code |
| `p_activation_pin` | text | Admin-issued, one-time/rotatable Remote Play activation secret |
| `p_client_install_id` | text | Random stable ID for this Android installation |
| `p_device_name` | text | Bounded Android device label |
| `p_app_version` | text | App version for audit |
| `p_access_token_hash` | text | SHA-256 hash of a fresh random 256-bit access token generated on device |
| `p_refresh_token_hash` | text | SHA-256 hash of a separate fresh random 256-bit refresh token generated on device |

Raw tokens are generated by the app and stored only using Android Keystore-backed encryption. The server stores only hashes. The activation PIN is never persisted by the app. A rental ID alone must never authenticate.

Expected result: `ok`, rental/account summary, customer access token expiry, and server time. The raw tokens are not returned by SQL because they were generated locally.

### Token refresh

`remote_play_refresh` is rate-limited and accepts `p_refresh_token_hash`, `p_new_access_token_hash`, and `p_new_refresh_token_hash`. The function validates and rotates the stored refresh hash atomically. The app generates and stores the replacement token pair only after a successful response. A reused/expired/revoked refresh token fails closed.

Customer API calls use auth family `remote_play_client`; Host Agent calls use a distinct `remote_play_host` family. An Admin/Billing/PC device token must never be accepted as either family.

## Customer RPCs

| RPC | Auth family | Arguments after Bearer token | Expected result |
|---|---|---|---|
| `remote_play_dashboard` | customer | none | Rental balance/expiry/access state, authorized host list, top-up details, active session and cooldown |
| `remote_play_request_session` | customer | `p_device_id uuid, p_idempotency_key text` | Exclusive session ID, server deadline/time, approved media route descriptor and pairing grant |
| `remote_play_session_mark_streaming` | customer | `p_session_id uuid` | Authoritative server deadline/time after Moonlight has connected |
| `remote_play_session_heartbeat` | customer | `p_session_id uuid` | Lease status, authoritative deadline and `stop_stream` instruction |
| `remote_play_end_session` | customer | `p_session_id uuid, p_reason text` | Idempotent settlement/close result |
| `remote_play_pairing_prepare` | customer | `p_session_id uuid, p_pin text, p_client_name text` | Short-lived pairing challenge accepted for the current session only |
| `remote_play_logout` | customer | none | Revokes the current customer token/session |
| `remote_play_topup_info` | customer | none | Exact configured QRIS asset URL and WhatsApp destination |

The dashboard must remain available for an expired or empty-balance rental. Only the start-session operation is blocked. Host cards are returned only for hosts that are Admin-authorized, online, and have a fresh Host Agent heartbeat.

### Host Agent RPCs

| RPC | Auth family | Arguments after Bearer token | Expected result |
|---|---|---|---|
| `remote_play_host_enroll` | one-time enrollment code | `p_enrollment_code text, p_host_token_hash text, p_agent_version text, p_media_route jsonb, p_metadata jsonb` | Binds the Agent to the Admin-approved existing PC record and issues the initial host registration |
| `remote_play_host_heartbeat` | host | `p_agent_version text, p_sunshine_ready boolean, p_media_route jsonb, p_metadata jsonb` | Host permission and liveness state |
| `remote_play_host_next_command` | host | none | Host-scoped pending commands only |
| `remote_play_host_ack` | host | `p_command_id uuid, p_status text, p_result jsonb` | Idempotent command acknowledgement |
| `remote_play_host_sessions` | host | none | Active leases assigned to this host only |
| `remote_play_host_pairing_poll` | host | `p_session_id uuid` | Pairing challenges for this host/session only |
| `remote_play_host_pairing_complete` | host | `p_session_id uuid, p_challenge_id uuid, p_success boolean, p_sunshine_pairing_id text` | Pairing outcome acknowledgement |
| `remote_play_host_end_session` | host | `p_session_id uuid, p_reason text` | Idempotent host-side close/settlement request |

Enrollment codes are one-use, short-lived, Admin-issued and bound to an existing `public.devices` identity. A Host Agent token is distinct from the existing PC Billing device token and is stored on Windows using DPAPI. The Agent must never receive PostgreSQL credentials or an Admin token.

## Server-side invariants (mandatory)

All checks and state transitions are in PostgreSQL transactions, not only app UI logic:

1. Lock the normalized organization + rental code using the same transaction-level lock used by PC Billing session start.
2. One rental account can have no more than one active session across Remote Play and PC Billing.
3. One host can have no more than one active Remote Play session.
4. Check explicit Admin permission on both the rental account and the host.
5. Check account state, expiry and positive shared remaining balance.
6. Set `deadline_at = min(now() + 3 hours, now() + remaining_seconds)`.
7. Settle consumed seconds exactly once, bounded by the session deadline and initial balance.
8. Enforce a 600-second cooldown in PostgreSQL after a session ends.
9. Lost heartbeats, app termination, host disconnection, explicit stop and hard deadline converge on the same idempotent settle/close path.
10. Host permission revocation or stale Host Agent heartbeat stops new starts and closes any lease according to the Admin revoke policy.
11. No customer or Host Agent may access PostgreSQL tables directly.

## Media route contract

A session grant can return only a per-session media descriptor, e.g. `media_transport`, `media_address`, `media_port`, and `route_expires_at`. The address is never typed by the customer. The DB API does not forward game traffic. The chosen route must transport Moonlight GameStream TCP **and UDP**, and be tested across mobile-carrier NAT/CGNAT. A plain HTTPS Worker, the existing DB API gateway, or the quick HTTP tunnel is not a media relay.

Sunshine's Web UI/REST API remains bound to localhost for Host Agent use only. The public network path must not expose the Sunshine admin interface.

- `REMOTE_PLAY_ACTIVATION_REQUIRED`
- `REMOTE_PLAY_ACCOUNT_INACTIVE`
- `REMOTE_PLAY_ACCOUNT_EXPIRED`
- `REMOTE_PLAY_BALANCE_EMPTY`
- `REMOTE_PLAY_HOST_DISABLED`
- `REMOTE_PLAY_HOST_OFFLINE`
- `REMOTE_PLAY_SESSION_ACTIVE`
- `REMOTE_PLAY_HOST_BUSY`
- `REMOTE_PLAY_COOLDOWN_ACTIVE`

## Release gate

This is a contract only. It does not claim the Node API or SQL functions exist. Before the APK is final, the separate DB Android backend must implement and test these exact RPCs, include them in the existing Node allowlist with per-family auth/rate limits, and pass cross-session Billing concurrency/settlement tests on disposable + staging databases. The actual stable HTTPS base URL must also be verified from another network. No live Redmi database migration is performed from this repository.
